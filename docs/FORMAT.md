# `.vora` container format — v2 implementation note

This is a versioned implementation specification, not a finalized or independently audited public protocol.

## Binary layout (v2)

| Offset | Field | Encoding |
|---|---|---|
| 0 | Magic / format marker | 8 bytes: ASCII `PRVORA02` |
| 8 | KDF salt | 16 random bytes (public; not a secret) |
| 24 | Manifest nonce | 12 random bytes |
| 36 | Encrypted manifest length | 4-byte unsigned little-endian integer, includes the 16-byte GCM tag |
| 40 | Encrypted manifest | AES-256-GCM ciphertext plus tag; maximum plaintext manifest is 4 MiB |
| after encrypted manifest | Encrypted archive | Concatenated AES-256-GCM chunks, each followed by its 16-byte tag |

All manifest fields are inside the encrypted manifest in v2: package ID and name, creation time, start/expiry dates, recipient label, issuer note, local activation limit, file count and total bytes, archive length, chunk size, payload nonce prefix and human-readable crypto labels. The package's external filesystem name and approximate total file size are not hidden by container encryption. The fixed magic, random salt, random manifest nonce and encrypted-manifest length are public by design.

The length and fixed KDF are part of the format contract. Knowing the algorithm name is not a cryptographic secret and does not meaningfully weaken a randomly generated 256-bit access secret; manifest encryption is primarily for metadata confidentiality, not algorithm obscurity.

## Cryptography (v2)

- A random 32-byte access secret is displayed as a Base32 `PV2-…` code. Dashes and prefix are presentation-only. The reader accepts the older `PV1-…` prefix when opening legacy v1 files.
- Argon2id v1.3 derives a 32-byte master key from the high-entropy secret and public random 16-byte salt using 32 MiB memory, 3 iterations and parallelism 1.
- HKDF-SHA256 derives independent metadata and payload keys using fixed labels `privora/v2/metadata-key` and `privora/v2/payload-key`.
- The manifest uses AES-256-GCM with its own random 96-bit nonce. Associated data is the exact 40-byte public header (magic, salt, manifest nonce and encrypted-manifest length), binding these values to the encrypted metadata.
- The ZIP archive is encrypted as 1 MiB chunks with AES-256-GCM. Each payload nonce is `random 64-bit prefix || 32-bit big-endian chunk index`; the chunk index begins at zero and never repeats within a package.
- Associated data for each payload chunk is `exact decrypted manifest bytes || 32-bit big-endian chunk index`. Manifest changes therefore also invalidate payload authentication.
- The stored archive length determines expected chunk lengths. Trailing bytes are rejected.

## Legacy v1 compatibility

The reader continues to read `PRVORA01` packages. V1 used a plaintext JSON manifest at offset 12, followed by encrypted ZIP chunks. V1 metadata is therefore still visible and cannot be retroactively concealed; re-create it as v2 to protect metadata. V2 packages cannot be opened by old v1-only builds.

## Safe extraction

Entries generated by both versions use top-level file names only. The reader rejects path separators, parent traversal, control characters and Windows special filename characters; limits entry count and expanded data size; extracts to a temporary staging folder; and renames the staging folder to a fresh destination.

## Versioning

Do not silently change magic, KDF settings, cipher, nonce construction, chunk size, manifest semantics or extraction behavior. Define a new version and compatibility plan for protocol changes.
